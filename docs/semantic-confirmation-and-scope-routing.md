# 语义确认与事实范围路由方案

| 项目 | 内容 |
| --- | --- |
| 文档版本 | 3.0 |
| 评审日期 | 2026-09-03（作用域路由部分取代 2026-09-02 v2.0） |
| 适用路径 | 自然语言问数（Natural-language question） |
| 决策阶段 | `CANDIDATE_DISCOVERY` |

## 1. 决策摘要

1. 普通用户不感知也不选择 QueryScope。Scope 是发布版本内由编译器生成的内部执行边界，只能出现在高级诊断与审计 Trace 中。
2. **弱召回（keyword / Term remap / embedding）只是给最终 LLM 的提示**，以 `mapped_constraints` 形式进入 Prompt。它不形成确认卡、不写记忆、不产生 settlement obligation，也不能锁定事实根。
3. 受治理指标的 direct exact 证据，或用户对同名语义元素的明确确认，可以锁定指标 owner（事实根）A。
4. **作用域不在生成前选定**：最终 LLM 看到候选作用域全部成员的并集，作用域由生成结果确定性反推（第 5 节）。
5. 指标锁定 owner A 后，所有 direct exact 维度和维度值仍是硬约束。A 内不可达时返回 `DIMENSION_NOT_REACHABLE`，不得丢弃维度，也不得切换到事实根 B。
6. 事实边界的确定方式不改变自然语言路径的 textual S2SQL 解析、纠正、翻译顺序和权威性。

## 2. 术语与证据权力

| 术语 | 定义 | 决策权力 |
| --- | --- | --- |
| Scope / QueryScope | Release 内编译冻结的单事实根、成员与路径集合 | 仅内部规划、校验和高级诊断；普通用户不可见 |
| owner / 事实根 A | 指标所属的受治理 Model | direct exact 或 confirmed metric 可锁定 |
| direct exact metric | Mapper 对已发布指标规范名或受治理别名产生的直接 `EXACT`；不包括 Term remap、manifest 和 all-field | 可参与自动锁定 owner |
| confirmed metric | 用户在**同名语义元素**确认卡中明确选择的元素 | 可锁定 owner，但不能改写成 exact |
| weak evidence | keyword、Term remap 或 embedding 召回 | 仅作为 Prompt 提示；不锁 owner、不触发确认 |
| exact dimension | direct exact 维度，或 direct exact 维度值所归属的维度 | 硬约束；可否决已锁定 owner 的可执行性 |
| business object | 面向用户的事实模型业务名称与说明 | 收窄后仍有多个事实边界时用于确认 |

`exact_metric_ids` 与 `confirmed_metric_ids` 必须分别记录。用户确认只增加 `confirmed_metric_ids`，不得把 `method=embedding|keyword|term` 篡改为 `EXACT`。

## 3. 总体流程

```text
用户自然语言问题
  -> 分词与召回（第 4 节）：受治理词表切分 ∪ 滑窗，剔除与精确命中重叠的碎片
  -> 全局证据收集（跨 Scope 一次）
  -> QueryScopeResolver：证据时效、权限范围与各道 fail-closed（不再选定作用域）
  -> 候选作用域【全部成员的并集】+ mapped_constraints -> 最终 LLM（第 5 节）
  -> 逐个真实作用域尝试翻译 -> 唯一即绑定 / 零个拒答 / 并列取最粗
  -> textual S2SQL -> Corrector -> Translator -> Guard -> Executor
  -> settlement：人工确认过的成员必须真的被用上
```

## 4. 分词：滑窗碎片与精确命中的关系

向量召回的查询片段是**受治理词表切分与滑窗的并集**。滑窗移植自上游 `BatchMatchStrategy`（size 3 / step 2），只从偶数偏移起切，所以一个词能否被查询取决于它在问句中的位置奇偶；词表切分负责真词，滑窗负责词表外说法。

**滑窗碎片若与词表精确命中重叠同一 span，就是那个命中的碎片，不参与召回。**

```text
问句：上海有哪些门店，什么时候开业的
词表精确命中：上海 [0,2)   门店 [5,7)
滑窗（偶数偏移）：上海有 [0,3)  有哪些 [3,6)  些门店 [4,7)  店，什 [6,9) ...

剔除：上海有、些门店、店，什（与精确 span 重叠）
保留：有哪些、什么时、开业的（不与任何精确命中重叠）
```

不做这一步的后果是实测到的死循环：`些门店` 去查向量召回「门店数量」→ 一个没问指标的问题被升级成"请确认指标"→ 用户确认后 settlement 判定生成的 SQL 根本没用这个指标 → 再次弹卡。上游 `MapFilter` 同形：精确命中拥有的 span 上剔除模糊命中。

不与任何精确命中重叠的碎片必须保留，否则词表外说法失去兜底。

## 5. 作用域：生成之后再反推

### 5.1 为什么不能先选

作用域选择要回答「这个问题在问什么」——那是理解题。路由器按合同不读问句、只看词典命中，用局部信息做了一个**不可逆**的决定；判错之后模型被锁在错误范围里，只能拿手头的成员硬凑：

```text
问：这些门店的销量是多少
「销量」召回销售数量与销售金额（都只在销售明细分析可见）—— 路由只看精确证据，把它丢了
剩下的精确证据只有「门店」「所在城市」，全归门店实体 → 选中门店分析
门店分析里唯一的指标是默认计数「门店数量」→ 模型只能用它
六道治理关全部放行：门店数量确实属于门店分析，没有任何不一致
```

上游 `HeuristicDataSetResolver` 是同一个结构性缺陷，只是四级相似度排序取第一、DataSet 名字命中优先，同一道题也会选门店，且没有任何澄清机制可退。

### 5.2 改为：模型提议，编译器裁定

```text
Mapper 全局证据
   ↓
最终 LLM 看到【候选作用域全部成员的并集】，写出业务名 S2SQL
   ↓
编译器逐个真实作用域尝试确定性翻译
   恰好一个成功 → 绑定执行
   零个        → 跨了事实根，拒答（实测模型确实会写出来）
   多个        → 粒度收敛取最粗；仍并列见 5.4
```

模型自始至终没有拿到 Scope 权威。**校验比选择容易**：翻译本身已经在验证成员归属、冻结路由可达性与全部治理规则，比另写一套集合判断更严，也少一处会漂移的实现。

对照实验（demo_cafe 20 题 + 合成不相连事实根 7 题，全部执行核对数字）：

| | 生成前路由 | 生成后反推 |
| --- | --- | --- |
| 直答且正确 | 14 | **22** |
| 澄清 / 拒答 | 10 | 4 |
| **静默错答** | **2** | **0** |

并集成员只比最宽作用域多 1.27 倍，且放大倍数与路由难度**负相关**：作用域重叠越重（路由越难判）并集越省；互不相干时并集大，但那时证据不跨域、路由本来就不会错。

### 5.3 跨作用域重名：给限定名，不回避

两个作用域各自都叫「净收入」，各自内部无歧义；并集把它们摆到一起就造出了单作用域里不存在的重名。按"有重名就不用并集"回退等于并集永远用不上——真实仓库里每张事实表都有「金额」「数量」。

复用建模期 `qualify_cross_model_metric_aliases` 的同一条确定性规则，写法沿用项目已有的「模型名.成员名」：

```text
成员名是模型名的子串 → 模型名
否则               → 模型名.成员名
限定名已被占用      → 回退，残余冲突交建模诊断
```

三点讲究：限定名**只活在生成阶段**；裸名连别名一起去掉（留着符号表又会变回歧义，召回走索引不受影响）；翻译前按**成员 ID** 还原——只换字符串会让目标作用域把不属于它的同名成员静默替换成自己那个，跨根查询于是"翻译成功"。

### 5.4 并集不启用的三种边界

都是实测逼出来的，不是为了绕开问题：

| 情况 | 为什么救不了 |
| --- | --- |
| 没有 LLM | Rule 只做模式匹配，更大的词汇表只会让它把不同事实根的成员混进一条查询，那样的查询没有作用域能翻译，本来能答的问题反而整条失败 |
| 同一模型内部重名 | 限定名一样，区分不了 |
| 某个候选作用域**内部**就有这组重名 | 翻译在真实作用域上进行，符号表只认规范名，还原回去照样 `LLM_S2SQL_AMBIGUOUS_SYMBOL`——那本来就是既有同名卡的场合 |

绑定并列也分两种：**同一事实根**的多个内部作用域是编译产物重复，用户看不见差异也判断不了（`QUERY_SCOPE_DUPLICATE_ROOTS`，面向建模者拒答）；**不同事实根**的并列才出卡，选项只列能区分这几个范围的成员——选中成员即定下拥有它的范围，作用域本身仍不出现在选项里。

### 5.5 上线前的四项验证（2026-09-03）

对照实验只证明了"选得对不对"。并集还接在四条既有链路上，逐条打了真断言（全部经变异验证：把修复去掉必须变红）。

**① 列级权限。** 并集不按 `allowed_element_ids` 裁成员，白名单在 Prompt 构造（`parser._visible`）和翻译两处生效，两层都在。断言：白名单外的成员名一个字都不出现在模型实际收到的 messages 里；模型硬写一个被隐藏的成员必须翻译失败、不执行。

**② Corrector 与 ALL 重试。** 校正器、最终 LLM、ALL 重投影跑的是同一份生成期目录，所以重试仍然看得见并集——否则第一遍写得出来的查询第二遍反而写不出来。另外澄清用的 `ClarificationSignal` 不是 `AnalyticsError`，不会被 `except AnalyticsError` 收进 ALL 重试当成"这遍没写好"。

**③ 多轮改写。** 修了一处：绑定后只改了 `dataset_id`，`corrected_s2sql` 还留着生成期的限定名与并集表名。它不只是给人看的——查询规则命中时会拿它去真实作用域上**重新翻译**，多轮改写把它交给下一轮的模型，回答卡的口径说明也读它。现在绑定时把翻译用的那份 SQL 一起换过去。

**④ 真实规模的 Prompt。** 用真实的并集构造 + 真实的 Prompt 构造实测：

| 形态 | 表数 | 最宽作用域 | 并集 | 放大 |
| --- | --- | --- | --- | --- |
| 线上发布（demo_cafe，4 作用域） | 4 | 4751 字符 | 5035 | **1.06x** |
| 星型 3 事实 / 6 维 | 9 | 3106 | 3954 | 1.27x |
| 星型 5 事实 / 8 维 | 13 | 3378 | 5498 | 1.63x |
| 12 个互不相干事实根 / 20 维 | 32 | 4711 | 14046 | 2.98x |

放大只在作用域**互不重叠**时才明显——星型仓库里最细的作用域本来就装着几乎全部维度，并集只多出别的事实根的指标。反推的第二项成本（逐作用域翻译）在 12 个作用域时合计 8.6 ms，每次恰好绑定一个。

顺手修掉的两个真 bug：`MatchMethod.CONFIRMED` 不在 mapper 去重的优先级表里（用户在卡上选的成员一旦和别的证据撞上就 `KeyError` 崩）；并集反推出的作用域歧义此前发的是普通语义卡，续跑时走另一条校验分支重算不出"当时展示过什么"，点了就是 `CANDIDATE_NOT_FOUND`——现在与路由器那条统一，选项自带所属作用域。

### 5.6 零绑定不等于跨事实根

一个作用域都翻译不出来有两种原因，对用户完全不同。实测（demo_cafe，「每个门店卖得最好的商品是什么」）模型写了 CTE + 窗口函数，外层引用 CTE 自己定义的列别名 `_总销售金额_`；用到的成员其实全在「销售明细分析」一个作用域里，翻译器说的是"不认识这个名字"，用户收到的却是"请拆开提问"——一个不用拆的问题被支开了。

不自己下诊断：零绑定时把同一条 SQL 对着**并集**再翻译一次，用翻译器自己的错误回答。真跨事实根时它本来就报 `CROSS_FACT_METRICS_UNSUPPORTED`；别的毛病它会说是哪个毛病。并集居然翻译得出来，那才是"成员各自合法、放一起不行"，这时「拆开提问」是对的。

2026-09-03 补：`_retarget_tables` 曾无差别改写所有表名，把查询自己定义的 CTE 名字
（`FROM agg`）也换成作用域名——并集路径下**任何带 CTE 的查询**都被这样打断过，表现正是
上面那种"零绑定"。现在只改作用域表。详见待办第 21 条。

### 5.7 遗留记录：可达不等于归属

Dataset 的成员关系表达的是**可达**——事实 scope 经冻结路由能到达它关联的每个实体。因此：

```text
问：上海有哪些门店，什么时候开业的
可达该证据的 scope：门店分析、销售单分析、销售明细分析（三个都能到门店属性）
```

把这三个摆给用户选，等于把内部执行计划当业务问题问出去。用户点名的是门店的属性，一个销售的词都没提。

> 2026-09-03 起这条收窄规则已删除，作用域由 5.2 的反推决定。保留这一节是因为「可达不等于归属」
> 这个观察本身仍然成立，也记录了为什么"用局部信息先选"必然有一类问题判错。

**已删除的收窄规则**：每组精确证据里只要有一个成员归候选事实根所有，该组就不算借用；借用组数最少的候选留下。

```text
borrowed(scope) = |{ 证据组 g : g 中没有任何成员由 scope 的事实根拥有 }|
candidates = argmin borrowed
```

- 借用 0 组即"全部证据都是它自己的"。
- 同一短语落到**不同实体**的维度（跨实体同名，如「US」既是客户地区又是平台地区）是语义歧义不是借用，该组不参与计数——否则会因为某个实体恰好没有独立 scope 而把歧义悄悄判给另一边。
- 只消费 exact 证据，不读问题文本，不比较任何分数。
- 零证据时所有候选借用数相同，规则不产生任何影响，继续走粒度收敛与既有 fail-closed。
- 有 exact / confirmed metric 时事实根由指标所有者决定，本规则不参与。

实机 demo_cafe：

| 问题 | 收窄后 | 说明 |
| --- | --- | --- |
| 上海有哪些门店，什么时候开业的 | 门店分析 | 全部证据归门店所有 |
| 咖啡单价大于 20 有哪些 | 商品分析 | 单价归商品所有，销售明细借用 |
| 每个门店卖得最好的商品是什么 | 销售明细分析 | 门店与商品分属两个实体，只有销售明细同时到达 |
| 各门店的销售额 | 销售明细分析 | 有指标锚点，由指标所有者决定 |

## 6. Embedding `0.9` 的含义

```text
relevance = (cosine + 1) / 2
relevance >= 0.90  <=>  cosine >= 0.80
```

默认 `embedding_similarity=0.90` 比较的是上游口径的 relevance，不是原始 cosine。它是**召回准入阈值**，不是正确率、概率或自动执行阈值：过阈只表示这条弱证据值得放进 Prompt 让最终 LLM 参考，本身不锁 owner、不触发确认。

## 7. exact 维度否决合同

锁定事实根的目的是缩小执行边界，不是让指标覆盖用户的其它明确语义。

```text
confirmed/exact metric M -> owner A
exact dimensions D = {D1, D2, ...}

feasible(A) = published scopes rooted at A
              ∩ scopes containing M
              ∩ scopes whose frozen route reaches every exact D

feasible(A) = empty and A has a published metric scope
    -> DIMENSION_NOT_REACHABLE
```

禁止忽略不可达维度后继续查询，也禁止偷偷切换事实根。

## 8. textual S2SQL 管线保持不变

事实边界只在 `CANDIDATE_DISCOVERY` 内确定。选中 Scope 后进入完全未变的既有管线：

```text
Mapper + selected SemanticParseInfo
  -> LLMSqlParser / RuleSqlParser（既有固定顺序与 fallback）
  -> textual parsedS2SQL
  -> QueryTypeParser + registered Correctors
  -> textual correctedS2SQL（继续保持权威）
  -> SqlQueryParser -> DimExpression/MetricExpression/MetricRatio -> OntologyQueryParser
  -> semantic Translator
```

路由器不得读取问题关键词补造语义，不得生成 S2SQL，不得要求 LLM 输出内部 metadata ID。最终 LLM 拿到选中 Scope 的**全部成员**而不是 Mapper 命中的子集——过滤版让一次漏召回直接等于"模型表达不出来"，产出丢 GROUP BY 的错误数字。

## 9. 普通用户与高级诊断的边界

| 表面 | 可以展示 | 不可以展示 |
| --- | --- | --- |
| 普通问数与确认卡片 | 指标名与说明、业务对象名与说明、不可解析的 continuation token | `QueryScope`、Dataset 内部名/ID、root model ID、Route、Join 路径 |
| 普通错误提示 | “指标与维度不可组合”“请选择你实际表达的业务含义” | 要求用户理解或配置 Scope 的修复步骤 |
| 高级诊断 / Trace | Release、index、原始 Mapper provenance、exact/confirmed IDs、内部 Scope 决策、冻结 Route | 用诊断数据反向参与在线语义选择 |
| 建模诊断 | Scope 覆盖率、路径、扇出、命名冲突 | 把 QueryScope 变成普通用户必须编辑的资源 |

普通 clarification wire 不序列化 option 的 `dataset_id`。所有澄清卡使用短期 `sel1` HMAC opaque token，绑定 project、actor、原问题、原始 dataset_ids 集、Release/spec/index、实际展示的组合与 TTL；先验签再解析发布目录。未展示候选、篡改、跨上下文重放、过期一律 fail-closed。

## 10. 保留的确认与 settlement

删减后仍然存在的阻断式确认只有三种：

1. **同名语义元素**：同一说法对应多个同名成员，LLM 无法用名字表达选择。
2. **生成后仍并列**：多个互不嵌套的事实根都能翻译同一条查询，粒度收敛也解不开。
3. **跨事实根同短语指标**：一个精确短语落到不同事实根的多个指标。

人工明确选择的语义必须形成 `FINAL_PARSING` settlement obligation：authoritative textual S2SQL 经 Translator 解析后必须实际使用所选成员且 root 一致；0 个、多个、被其它成员替换或 Rule fallback 漏掉选择都不得执行。settlement 只能接受 / 澄清 / 拒绝，不能改写 S2SQL。

## 11. 已删除的机制（不得重新引入）

| 机制 | 删除理由 |
| --- | --- |
| weak metric 确认卡（`_weak_metric_confirmation` 全链路） | 把弱召回提升成绑定用户的决定；没问指标的问题被迫确认指标，再被 settlement 判定未使用而循环 |
| AI weak-metric 裁决（`weak_metric_adjudication_mode`） | 服务于上面那张卡；卡消失后没有触发点 |
| 业务意图 / 分析对象裁决（`analysis_object_adjudication_mode`、`semantic_intent_adjudication_mode`） | 作用域改为确定性归属收窄，不再需要模型选业务对象 |
| 确认记忆（`analytics_confirmation_memory` 及别名建议 API） | 记忆的是已删除的那些卡的选择；且绑定 index id，索引重建即静默作废 |
| 多指标组合确认续跑（`selected_metric_bundle_ids`） | 组合卡本身已删除 |

## 12. 已知限制

承载事实意图的**动词**没有任何映射，而全部精确证据归某个实体所有时，收窄会选中该实体 scope：

```text
问：上海的门店都卖了些什么
证据：上海（门店城市值）、门店（门店名称维度）——「卖了些什么」映射不到任何成员
结果：门店分析 -> SELECT "门店名称" FROM "门店分析" WHERE "所在城市"='上海'
```

2026-09-03 起这题已由生成后反推答对（模型看到全部成员，写出 `SELECT DISTINCT "商品名称" WHERE "所在城市"='上海'`，只有销售明细分析能翻译）。下面这段保留为记录：它当时不是收窄规则的缺陷，旧的业务对象卡同样保护不了它（选项是"销售单 / 销售明细 / 门店"，用户看到自己说的「门店」就会选门店，得到同一个错答）。正解是在业务词典中补别名，让「卖」这类说法映射到销售指标或销售明细，而不是恢复卡片。作用域路由按合同不读问题文本，不能凭动词改判。

## 12.1 空结果的两种含义

空结果是数据事实，"系统没能表达问题"不是。两者必须分开：

| 形态 | 处理 |
| --- | --- |
| 模型用永不成立的条件（`1=0`、`FALSE`）顶掉表达不了的部分 | `S2SQL_CONTRADICTORY_FILTER` 拒绝。判据是 sqlglot 常量折叠：任一 SELECT 的 WHERE/HAVING 归约为 FALSE。`1=1` 等无害占位、OR 分支、子查询过滤都不受影响 |
| 0 行且过滤值不在该维度已发布取值里 | 指名道姓说出来；编辑相似度 ≥0.6 才给近似建议（卡布奇洛→卡布奇诺 0.75 建议；摩卡 0.33 不猜） |

只判文本取值、只看已发布取值的维度、只在过滤投影完整时判。措辞是"不在已发布取值里"
而不是"不存在"——高基数维度的取值可能只是抽样。
