# 问数核心重构技术方案

状态：2026-09-21 已评审、已实施、**已回退**。

这份文档现在的用途是**测量记录**，不是待办清单：原方案估计能减 ~3000 行，实测逐条塌掉，
改完零行为变化、源码净 −30 行，用户判定意义不大并回退到 HEAD。想再简化问数核心时，
先读 §5.5「被测量推翻的」和「未做，且各有前置条件」两节，再决定值不值得。

留下来能直接复用的是秤和三个独立缺陷：`scripts/query_replay_benchmark.py` +
`scripts/query_suites/{acct,alert}.json`（§4.5），以及方言猜测、重试反馈把正确尝试
推成错指标、`ENTITY_SHARE` 的维度边界。那次改动的 patch 在
`docs/query-core-refactor.patch`（`git apply` 可还原，不建议直接用）。

本方案只做一件事：**把问数从"两套引擎互相协调"收敛成"模型提议 + 编译器裁定"一条路**。
它不增加任何能力，不改变任何治理判定的严格程度，也不引入新概念。

---

## 0. 判据

先定边界，再谈简化。三层职责：

```
① 建模（人 + AI 助手）      决定业务语义。允许含糊、允许留白。
         ↓ Catalog
② 编译 + 发布门禁            把含糊变成确定，或者拒绝发布。fail-closed 在这里。
         ↓ SemanticRelease   ← 真正的边界
③ 问数                       翻译 + 校验 + 执行。零判断。
```

**不变量 B0：一个发布出来的 Release，必须让问数成为一个没有判断余地的纯函数。**

推论：问数期凡是需要在多个合理答案里挑一个的，都是 ② 的缺口，不是 ③ 的 bug。
问数期只允许三种结局——翻译成功、确定性拒绝、或者把一个**用户真的能回答**的问题问出去。

判据的操作形式：对任一问数期决定问"两个明白人会不会有不同答案？"，会，就是在猜。

## 1. 现状测量

代码规模（2026-09-21）：

| | |
|---|---|
| NL2SQL 总量 | `query/` 16,274 + `semantic/` 5,189 = 21,463 行 |
| `service.py` | 5,202 行（仓库规范 <800）；`_query` 单方法 1,339 行 |

| 翻译器 | 3,429 行、8 个解析器 |

没有 LLM 的部署在生产中不存在，只活在测试里。

### 1.1 三条主线的诊断

**① Rule 解析器是一套从不答题、却有否决权的引擎。**
`final_parse` 从 Rule 候选里只取两个标量：`dataset_id`（本就来自作用域路由）与
`mapping.mode`，随后 `final_mapping` 把 `selected.mapping` 整个换掉；CLAUDE.md 另有
"最终 Prompt 不得包含 Rule S2SQL 文本"。所以 Rule 构建的聚合意图、TopN、排序、值过滤、
时间过滤、完整 SemanticQuery、序列化与再校验**全部作废**。而它构建过程中抛的
`ClarificationSignal` 会让发现阶段零候选，LLM 连入口都没有——实机
「检查 2024 年 1 月所有凭证是否借贷平衡」即如此挂掉。
围绕它还养着一整套文档化合同（candidate admission、no-resurrection、ALL-retry 重新生成
Rule 候选，见 `supersonic-parser-fallback-parity.md`），服务的是一个 0/47 的路径。

**② 作用域路由存在两套，互相拆台。**
1,151 行的确定性路由器在**理解问题之前**选作用域，生成后的并集反推又把它推翻。
两套都在跑（SELECTED 40 / DERIVED 28）。2026-09-03 评审已判"顺序错了"，但只落了一半：
生成那半改了，收窄那半留着，于是 `_least_borrowing_scope_ids` 仍在线——本次会话的
「2024 年 1 月销售部差旅费 → 会计科目数量 0」正是它造成的。
并集本身又是一层：铺平假表、派限定名、还原限定名、撞名就整份放弃；而"撞名"在真实客户目录里
由外键 ID 列触发，导致多作用域生成**从未启用过**。

**③ 召回的 2,004 行大部分在产出建议。**
按 2026-08-28 评审，最终 LLM 拿的是选定作用域的**全部成员**，不是 Mapper 命中的子集。
因此 7 通道 × 6 方法只有两个承重输出：维度值落地（高基数，塞不进提示词）与同名卡
（重名时模型无法用名字表达选择）。其余进 `mapped_constraints`，模型看不看结果一样。
而它同时是失败主因：`GROUNDED_VALUE_REQUIRED` 10/85 = **12%**，全部来自复合词被切成
已发布取值（资产负债**表** → 资产 + 负债）。

### 1.2 缺口的归属

本次会话查的四个 bug，根因分布：

| 现象 | 真因 | 归属 |
|---|---|---|
| 差旅费答成「会计科目数量 0」 | 词典链接零消费 + 标识列发布成可问维度 + 星型归属收窄 | ② |
| 资产负债表答不出 | 复合词不在词典，被切成已发布取值 | ③（校验判错，模型写对了） |
| 借贷平衡弹卡 | 5 个时间维、零个 `partition_time` | ② |
| 应交增值税答空值 | 作用域选错 + 零行聚合标 success | ② + ③ |

**四个里三个在 ②，而历史上全部在 ③ 打了补丁。** 这是复杂度的来源。

## 2. 目标架构

```
问题 + 按作用域分组的完整目录（各用各的规范名）+ 值证据
    ↓ 一次 LLM（失败时带拒绝原因重试）
业务名 S2SQL，FROM 子句即作用域声明
    ↓ 确定性校验（全部保留，一条不减）
AST 形状 · 作用域绑定 · 成员归属 · 路由可达 · 扇出 · 粒度 · 时间治理
· 数值阈值 · 比率形状 · 矛盾过滤 · 权限 · 值落地
    ↓
翻译 → Guard → 执行 → 解释
```

五个阶段取代九个：

| 阶段 | 职责 | 明确不做 |
|---|---|---|
| **PREPARE** | Release、权限白名单、按作用域分组的目录、值证据、样例、多轮门 | 不选作用域、不建候选、不打分 |
| **GENERATE** | 一次模型调用产出业务名 S2SQL；内层重试带上次拒绝原因 | 不做语义裁决、不接触物理表名 |
| **VALIDATE** | 上面整条确定性链，逐条 fail-closed | 不改写 S2SQL、不挑候选 |
| **TRANSLATE** | 业务名 → 参数化物理 SQL + Guard | 不变 |
| **EXECUTE** | 执行 + 投影 + 可选解读 | 不变 |

**"模型提议、编译器裁定"是唯一主轴。** 校验比选择容易——翻译本身已在验证成员归属、
冻结路由可达性与全部治理规则，比另写一套集合判断更严也少一处漂移。

## 3. 逐项决策

| 现有机制 | 决策 | 依据 |
|---|---|---|
| `RuleS2SqlParser` 作为 NL 路径的查询引擎 | **删除** | 0/47 从未答题；只贡献 2 个标量；其澄清能毙掉正确答案 |
| Rule×LLM fallback 合同（admission / no-resurrection / ALL-Rule） | **删除** | 无 LLM 的部署不存在，整条分支在生产从未执行 |
| `MapMode` STRICT/MODERATE/LOOSE 三档 + 逐数据集发现循环 | **删除** | 只为给 Rule 候选分档 |
| `_top_candidate` / `score` 排序 / `_cross_dataset_sort_key` | **删除** | 违反 B0；用户 2026-08-31 已明确否决 score-gap 式打分 |
| `clarifications[0]`（3 处取第一个） | **删除** | 违反 B0；澄清收敛后自然消失 |
| `_least_borrowing_scope_ids` 归属收窄 / `anchor_dataset_ids` 锚点收窄 | **删除** | 2026-09-03 已判死刑，代码未删；本次差旅费 bug 的直接根因 |
| 并集假表 `dataset:union:generation` + `_retarget_tables` | **删除** | `FROM` 声明已替代（本轮已实现并上线） |
| `_qualified_union_names` / `_restore_union_names` | **降级保留** | 跨作用域重名时模型仍需能表达选择；但从"并集内改写"变成"目录渲染规则"，还原退化为一次成员 ID 查表 |
| `S2SQL_CORRECTING` / `PHYSICAL_SQL_CORRECTING` 两个阶段 | **删除** | 默认 `enabled=[]`，生产从未执行 |
| `self_consistency_number` 投票 | **删除** | 默认 1；且它记不到 `model_calls` 观测里 |
| Mapper 的指标/维度权威 | **降级为提示** | 成员表已全给模型；`mapped_constraints` 保留，删除需先 A/B（见 §5 批 4） |
| Mapper 的维度值落地 | **保留并加强** | 唯一塞不进提示词的信息；是 12% 失败的战场 |
| 翻译器 8 个解析器 | **一条不减** | 错了能被确定性发现的，正是编译器该管的 |
| `AMBIGUOUS_TIME_DIMENSION` 澄清 | **移到发布门禁** | 问的是建模者该定的事 |
| `AMBIGUOUS_QUERY_SCOPE` 澄清 | **移到 FROM 声明** | 模型能表达，不必问用户 |
| 同名成员澄清卡 / settlement 义务 | **保留** | 用户真的能回答；合同已被测试冻结 |

粗估：`mapper` 2,004 → ~500，`scope_resolver` 1,151 → ~300（只剩时效/权限/可达校验），
`parser` 2,432 → ~1,400，`_query` 1,339 → 5~6 个 <200 行的阶段函数。
**约 −3,000 行，更重要的是删掉"两套机制互相协调"这一整个维度。**

## 4. 设计约束（踩过的坑，不得违反）

这些是实测逼出来的，新设计必须逐条满足：

1. **限定名还原必须按成员 ID，不能只换字符串**（2026-09-05）。只换字符串会让目标作用域把
   不属于它的同名成员静默替换成自己那个，跨根查询于是"翻译成功"。
2. **textual S2SQL 是唯一权威**（2026-09-05）。`DATE_TRUNC` 粒度、`RATIO_*` 期间比、别名
   只存在于文本里；任何走投影重跑的路径都会静默丢掉它们。续跑走 `query_s2sql`。
3. **滑窗碎片与精确命中重叠即剔除**（2026-09-02，与上游 `MapFilter` 同形）。否则
   「些门店」这类碎片会把没问指标的问题升级成指标确认，再被 settlement 判成没用上，无限弹卡。
4. **`index_identity_hash` 不得含 vectors**（2026-08-30）。远程 embedding 不逐位可复现。
5. **`spec_hash` 是存储字段，不是派生字段**（2026-09-21，本次踩）。`model_copy` 改了 terms
   却不改 `spec_hash`，`find_index_snapshot` 会复用旧索引——据此得出的"Term 不生效"结论是错的。
6. **权限白名单必须穿透到目录渲染**（2026-09-21，本次踩）。第一版 `_render_scope_catalog`
   忘了 `visible_element_ids`，被 `test_a_hidden_metric_never_reaches_the_prompt` 抓住。
7. **按数据集成员过滤必须同时作用于 Rule 与 `_semantic_context_payload`**（2026-09-21，本次踩）。
   漏一处就是 `LLM_S2SQL_AST_INVALID` / `INTERNAL_ERROR`。
8. **提示词的字节数不是可单独优化的量**（2026-09-18）。"信息没变、只换写法/顺序"不是安全改动；
   组合样例是承重墙。任何改动模型可见文本的提案，先在需要被考到的题上 A/B。
9. **规则块红线**（2026-09-17）。不得为某个错例往 `S2SQL_SYSTEM_RULES` 追加规则；句数由
   `test_prompt_rules_are_not_prose_debt` 冻结。
10. **扇出是算对而不是禁止**（2026-09-16）。`DISTINCT` 塌行 + 按主标识接回；没有主标识才拒。
11. **不抄上游的"无分区维度就删掉用户时间条件"**（2026-09-04）。问题里明确说的时间一个字不动。
12. **FK 冗余列偏好规则已被实测否决**（2026-09-21）。Q5「各月销售收入」3/3 写成借方，不要再提。

## 4.5 基准（改之前先有秤）

`scripts/query_replay_benchmark.py` + `scripts/query_suites/*.json`。
每一批改动前后各跑一遍，**基线必须跑两遍**——同一条问句两次翻面是常态
（CLAUDE.md 2026-09-18 实测 2/42），不量噪声地板就分不清"改好了"和"抖了一下"。

**两层判据**

| 层 | 覆盖 | 回答什么 |
|---|---|---|
| **指纹** | 全部题，不需要真值 | 有没有东西变了。state / dataset_id（作用域）/ 错误码 / `category/severity` / 列清单 / 行数 / `all_null` / S2SQL 原文 |
| **真值** | 写了 `truth_sql` 的题，直连客户库 | 变好还是变坏 |

重构的风险大半在第一层：删掉一个机制之后，多数题的**结局**不会变，变的是它走了哪个
作用域、翻出什么 SQL。指纹差异会被单独列成"结局没变但指纹变了"，交人看。

**结局分六种**，`wrong` 与 `empty` 是分开的：

- `correct` 数字对上
- `wrong` 有数据但数字不对 —— **静默错答**，0 底线那一项
- `empty` 0 行或全 NULL 而真值有数据 —— 界面说"没有返回数据"，用户读成"我业务上没这件事"，
  一句关于他自己业务的假话（2026-09-03 评审的那两种空结果）
- `clarify` / `refuse` / `answered`（无真值时）

排序上 `refuse` 高于 `empty` 与 `wrong`：拒答用户知道没拿到答案，后两者他以为拿到了。

**真值比对是包含而不是相等**：行数必须相同，真值的每个数字必须能在答案里找到。
分组键的表示法两边合法地不同——真值按 `period='2024-01'` 分组、模型按 `月份=1` 分组，
两个都对，但后者会多出 1、3 这些数字；要求相等会把对的答案判成错的（acct-05 实测被
这样误判过一次）。代价是查不出"多投影了一列无关数字"，那是已知的良性差异。

**两个题集**

- `acct.json` —— 会计项目 **20 题（用户设计，2026-09-21 替换了此前临时凑的 11 题）**，
  带真值，是"数字对不对"的秤。覆盖：科目精确 3 / 模糊 2、连字符易遗漏 2、跨年 1、
  部门 2、往来单位方向 2、税务税种 2、报表口径 1、科目余额 1、凭证类型 1、月份范围 1、
  季度 1、全年 1（高优先 14、中 6）。每题另带 `must_filter`——参考 SQL 必须命中的
  过滤条件，**它比行比对更强**（行数碰巧对上时查不出"漏了某个条件"），当前只作元数据
  保存、跑批不校验，接上它是这把秤最值得加的一层。
- `alert.json` —— 预警项目 26 题，**只有指纹**，是"有没有东西变了"的秤。
  近似重复的问法（"按日统计账号预警数量" vs "按日统计账户预警数量"）是故意保留的：
  它们考的是同一问题换个说法会不会翻面。

**⚠️ 两个必踩的坑**

- **两臂都必须走 `PYTHONPATH`，基线不能用容器的 `site-packages`。** 线上是热更过的，
  只替换了 `query/{orchestrator,parser,service}.py`，其余全旧——`syntax_exemplars.py`
  那里停在 4 条而 main 已是 11 条（2026-09-17 补的正是占比、窗口、集合运算那批）。
  于是"基线"其实是「几个热更文件 + 其余全旧」，据此得出的结论会把样例差异误判成代码
  改动的效果（实测 `alert-24` 就是这么被误判的）。用
  `git archive HEAD src/knowflow_analytics` 造基线臂、工作区造改动臂。
- **产物写 `/var/tmp`**，`/tmp` 里较新的文件会被容器清掉（实测整批 `*.json` 连同
  `.done` 一起消失，而同目录的脚本还在）。

**指纹层要先做别名归一**才有用：同一份代码跑两遍，S2SQL 有相当一部分只是别名在抖
（`"差旅费"` vs `"差旅费_"`、多写一个 `DISTINCT`），作用域、列、数字全同。
`_shape()` 归一之后指纹噪声从 7/10 降到 2~3/11，剩下的每一处都是真不稳定。

**基线（2026-09-21，HEAD `e173997` 的 src，每题 3 次、跑两遍）**
冻结在 `scripts/query_suites/baseline/acct_base20_{a,b}.json`，改动后直接 `--diff` 它。

```
总汇总    correct 13 · empty 4 · wrong 2 · clarify 1
噪声地板  0/20 —— 两遍逐题一致，连指纹都相同
```

**必须按「真值有没有数字」拆开读**，否则会把空过当成答对：

| | 道数 | 结局 |
|---|---|---|
| 有数字真值 | 14 | **correct 8 · empty 4 · wrong 2** |
| 真值为空（demo 库缺该期间/科目） | 6 | correct 5（空过，只考到零行诚实性）· clarify 1 |

所以真正的正确率是 **8/14**，13 个 correct 里有 5 个是"两边都空"。

**三类失败，成因各不相同**：

1. **作用域落到「科目余额分析」**（D002 / D015 / D019 → `empty`）。那张表只有 4 行、
   全是 2024-01，而真值在凭证分录里。模型写
   `SUM("本期借方发生额") FROM "科目余额分析" WHERE "科目名称"='管理费用-办公费'`——
   语义上讲得通，表里就是没有这行。
2. **漏掉过滤条件**（D005 → `wrong`）。问"2024年2月招待费"，写出
   `SUM("借方金额") FROM "凭证分录分析" WHERE "年份"=2024 AND "月份"=2`——**完全没有
   科目条件**，把 2024-02 全部借方加了起来（9500 = 1500 办公费 + 8000 招待费），真值 8000。

   对不上侥幸抓到了；如果 2024-02 只有招待费一笔，它会静默通过。**接上 `must_filter`
   的理由从此有实证。**
3. **用错字段表达业务概念**（D008 / D010）。D008 用 `"报表项目"='应收账款'` 表达应收方向，
   而真值是 `fact_ar_ap.direction=1`（报表项目在 `dim_account` 上，不在这张事实表上）；
   D010 用 `"摘要"='销项税额'` 表达税种，而字段是 `tax_type`、取值是 `销项`，还漏了年份。

**已知限制**（写下来，免得把基准的巧合当成结论）

- 会计库数据极小（`fact_voucher_entry` 18 行、`fact_voucher` 8 行），数字碰巧对上是可能的。

  这是本基准最重要的一条读法。
- 组合形态（窗口函数、相关子查询、`ENTITY_SHARE`、`RANK_OF`、集合运算、期间比）

### 量出来的第三个独立缺陷：重试反馈会把正确尝试变成静默错答

`alert-24`「账户余额大于 1000 占比情况如何」，11 条样例下模型第一次写的是

```sql
SELECT ENTITY_SHARE("账号", "账户余额" > 1000) AS "_占比_" FROM "账户模型预警分析"
```

**指标选对了。** 但编译器以 `S2SQL_RATIO_METRIC_REQUIRED`（ratio expression requires
exactly one governed metric）拒绝——账户余额在该作用域是维度、不是受治理指标。
重试把拒绝原因喂回去之后，模型改写成

```sql
SELECT ENTITY_SHARE("账号", "推送预警账户数量" > 1000) AS "_占比_" FROM "账户模型预警分析"
```

**这条过了全部校验，返回一个看起来像百分比的数字，而它算的是另一件事。**

重试反馈只陈述"上一次被什么码拒了"，模型据此找一个能过校验的写法——当被拒的原因是
"你要的那个东西不是指标"时，"能过校验"和"回答对了"就分道扬镳了。这是 `ENTITY_SHARE`
原语的边界：它要求比较项是受治理指标，而用户问的"账户余额"是维度。
属于建模缺口（②）：要么把账户余额发布成指标，要么让原语支持维度阈值。

### 这一轮暴露的两个原型缺口（都已修，记下来免得重犯）

- **JSON schema 不能把 `scope`/`metric` 标成 required**：模型判断"表达不了"时这些字段
  本来就没有值，标成必填会让**正确的拒答被网关拒掉**，看起来像模型出错。实测预警题集
  因此丢了 5~7 道。合法性由组装层判，不由 schema 判。
- **要有 `shape: aggregate|detail` 槽位**：`SemanticQueryType.DETAIL` 本来就支持明细查询，
  原型把它写死成 AGGREGATE，于是"列出账号、日期、触发原因"这类被误判成"槽位表达不了"。

### 表达力边界：必须是两条路

槽位表达不了 CTE、窗口函数、`RATIO_*` 期间比、`ENTITY_SHARE`/`RANK_OF`、集合运算——
那 11 条组合样例教的正是这些。所以不能整条替换，要按"槽位能不能表达"确定性分流：
能 → 槽位路（确定性组装，不可能生成非法 SQL）；不能 → 文本路（现有全链路一字不动）。
20 道基准全在槽位路上；分流比例要用 demo_cafe 那 42 道历史题量一遍才有底。

### 三件原以为没验的，验了（2026-09-21）

**① 权限收窄**——两处都守住了：目录渲染时隐藏成员不出现（包括业务词典里指向它的那条），
组装层硬填再拒一次。只做前者是"前端显隐当安全边界"，只做后者是把不该看的名字摆给模型，
它照着填再被拒，用户看到一句莫名其妙的拒答。

| 检查 | 结果 |
|---|---|
| 目录里还有没有被藏的指标 | 否 ✓ |
| 词典里指向它的那条还在不在 | 否 ✓ |
| 组装层硬填被藏的指标 | 拒 ✓ |
| 还原白名单后恢复 | 是 ✓ |

**留一个要你定的设计问题**：藏掉 `借方金额` 后，模型挑了 `本期借方发生额`（另一张表的
近似指标）并且组装通过。这不是泄漏——它只用了能看的东西——但**权限收窄会导致换指标
作答，而两个指标的数可能不同**。好处是槽位路里"用了哪个指标"是显式槽位、会出现在回答
卡上；文本路里它埋在 SQL 里。要不要在这种情况下改成拒答，是产品决定。

**② 下钻续跑**——四种编辑全部保住形状：

| 编辑 | 结果 |
|---|---|
| 换过滤值 2024-01 → 2024-03 | 仍按部门分组，3 个部门 ✓ |
| 加分组维度（部门 + 科目） | ✓ |
| 换指标（借方 → 贷方） | 125000 贷方，与借方相等，对 ✓ |
| 去掉分组回到合计 | 125000 ✓ |

下钻现在必须在**文本 AST** 上做五种确定性编辑（2026-09-05 评审：`semantic_query` 是投影，
`DATE_TRUNC` 粒度、`RATIO_*` 期间比、别名只存在于文本里，拿投影重跑会静默丢掉）。
**槽位路没有这个问题——槽位就是权威，编辑它不丢任何东西**，`query/s2sql_edit.py` 那套
AST 编辑只需要留给文本路。

**③ 多轮改写**——那道门变成槽位 diff：

```
原话  「2024年1月各部门的差旅费是多少」      group_by=['部门名称']
改写  「2024年1月各部门各科目的差旅费是多少」  group_by=['科目名称', '部门名称']
改写新增: ['科目名称']
```

2026-09-05 的门是"改写新增了原话没有的**分组维度**就作废回退"，实现上要比较两次 Mapper
的精确证据。槽位路里它**直接可见**：比两组 `group_by` 就行，零额外模型调用、零推断。

### 还没验的

预警项目那 26 道（纯指纹、无真值）、多轮改写、下钻续跑、权限收窄在槽位路上怎么走，
以及超时重试（原型没做，两次 19 就是它）。

## 6. 上游对照

| 上游做法 | 我们 | 判定 |
|---|---|---|
| `HeuristicDataSetResolver` 四级相似度取第一 | 曾照抄为归属/锚点收窄 | **不要**。同一道题也会选错，且上游没有任何澄清机制 |
| Rule + LLM 双解析器 fallback | 照抄了整套合同 | **上游包袱**。它需要 Rule 是因为 LLM 路径更弱（单数据集 schema）；我们的更强 |
| `MapFilter`（精确命中的 span 上剔除模糊命中） | 已对齐 | **保留**，它是对的 |
| `BaseMatchStrategy` O(n²) 子串窗口 + 编辑相似度 | 部分对齐 | **收窄**。上游同病且更宽；我们只需值落地 |
| `TimeRangeParser` / `TimeCorrector` | 部分对齐 | **保留**，但"无分区维度就删用户时间条件"那条不抄 |
| `DataSetSchema.getPartitionDimension()` 用 `findFirst()` | 同形 | **上游缺陷**。改为发布门禁强制唯一 |
| `cubeCardinalityQueries`（Cube 的唯一数据探针，零调用死代码） | 我们用真实数据核对主标识 | **我们更强**，保持 |
| `DataInterpretProcessor` | 已移植并加严三处 | 保持 |

一句话：**上游的召回与 Rule 兜底是为它自己更弱的生成路径设计的；照抄它们等于给我们更强的
生成路径套一副拐杖，而这副拐杖会绊倒它。**

## 7. 风险与不做的事

**风险**
- 101 条诊断来自 2 个项目、偏近期，不是完整生产样本。"Rule 0/47"有信心，但值得在更大题集上复核。
- 删 Rule 会影响结构化 Playground 吗？`_apply_time_filters` 被结构化路径也用着，那一侧不动。
- `SELECTED_SEMANTIC_NOT_USED`（3 次）的 settlement 义务与同名卡耦合，拆之前要单独看。

**明确不做**
- 不引入 jieba 或任何通用中文分词（实测：其词典不含任何会计复合词，救不了资产负债表）。
- 不引入 score / 阈值式的作用域选择（用户 2026-08-31 已否决）。
- 不为任何单个错例往提示词加规则（2026-09-17 红线）。
- 不合并内部 `/v1/*` 到 `/api/v1/*`，不跟上游 `restful_apis/` 目录重构。
- 不动 RATIO / 扇出 / 粒度 / 时间治理任一解析器的严格程度。

## 8. 建议的起点

顺序：**§5.2 第 3 条（归属标注）→ §5.1（发布门禁）→ §5 批 1–5（简化）**。

理由：归属标注不改任何行为、一天内能做完，做完之后线上诊断会立刻告诉你
"现在到底有多少问题是建模的"——那个数字决定后面两步各投多少。
